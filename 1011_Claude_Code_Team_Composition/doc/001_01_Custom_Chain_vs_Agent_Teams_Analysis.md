# 커스텀 체인 시스템 vs 공식 Agent Teams 충돌 분석

> 앤의 Dynamic Chain / Subagent 시스템과 Opus 4.6 공식 Agent Teams의 실행 로직 충돌 여부 및 성능 비교
> 작성일: 2026-02-06 | 기준: CLAUDE.md V3.8 + Opus 4.6 Agent Teams (실험적)

---

## 결론 요약

| 질문 | 답변 |
|------|------|
| **충돌하는가?** | **아니오.** 완전히 다른 추상화 레이어에서 동작 |
| **뭐가 더 나은가?** | **용도가 다름.** 일상 작업엔 커스텀 시스템이 효율적, 대규모 병렬엔 Agent Teams |
| **동시에 쓸 수 있나?** | **가능.** Agent Teams 팀메이트 안에서 커스텀 체인이 실행됨 |
| **활성화하면 기존 것이 깨지나?** | **아니오.** env 변수 켜도 명시적으로 팀 생성해야만 작동 |

## 1. 아키텍처 레벨 비교

### 앤의 커스텀 시스템 (CLAUDE.md V3.8)

```
메인 세션 (Opus 4.6)
├── Task(subagent) ─→ 서브에이전트 A [Sonnet]
├── Task(subagent) ─→ 서브에이전트 B [Opus]
├── Task(subagent) ─→ 서브에이전트 C [Sonnet]  ← 병렬
└── 결과 반환 → 메인에서 통합

⚡ 단일 프로세스, 내부 컨텍스트 분리
```

**구성 요소:**
- Dynamic Chain Patterns V2.0 (10개 체인)
- 커스텀 서브에이전트 24개 (Cognitive 10 + Role 4 + Management 2 + Utility 8)
- 4-Layer 자동 분석 (UserPromptSubmit Hook)
- PARALLEL-FIRST 원칙
- 모델 세분화 (opus = 심층 분석, sonnet = 구현/탐색)

### 공식 Agent Teams (Opus 4.6 신규)

```
리드 세션 (별도 프로세스)
├── 팀메이트 A (별도 Claude Code 프로세스) ──┐
├── 팀메이트 B (별도 Claude Code 프로세스) ──┼── 직접 통신
└── 팀메이트 C (별도 Claude Code 프로세스) ──┘
공유: 태스크 리스트 + 메일박스

⚡ 멀티 프로세스, 완전 독립 세션
```

**구성 요소:**
- 리드 세션 (조정, 할당, 통합)
- 팀메이트 (독립 Claude Code 인스턴스)
- 공유 태스크 리스트 (`~/.claude/tasks/{team-name}/`)
- 메일박스 (에이전트 간 메시징)
- tmux/iTerm2 분할 창 지원

## 2. 실행 로직 충돌 분석 (핵심)

| 비교 항목 | 커스텀 시스템 | Agent Teams | 충돌 여부 |
|----------|-------------|-------------|----------|
| **실행 단위** | `Task` 도구 호출 (세션 내부) | 별도 `claude` 프로세스 (외부) | **충돌 없음** |
| **태스크 관리** | `TaskCreate/Update` (세션 메모리) | `~/.claude/tasks/{team}/` (파일 기반) | **충돌 없음** - 네임스페이스 분리 |
| **통신 방식** | 서브에이전트 → 메인 반환 (단방향) | 메일박스 기반 양방향 메시징 | **충돌 없음** - 메커니즘 다름 |
| **컨텍스트** | 메인 세션 컨텍스트 일부 공유 | 각자 독립 컨텍스트 (1M 토큰) | **충돌 없음** |
| **모델 제어** | CLAUDE.md에서 지정 (opus/sonnet) | 팀메이트 생성 시 지정 | **충돌 없음** |
| **CLAUDE.md 로딩** | 메인 세션이 로드 | 팀메이트도 각자 로드 | **호환** |
| **Hook 시스템** | 메인 세션에서 실행 | 팀메이트는 리드 권한 상속 | **호환** |
| **권한 모델** | settings.json 기반 | 리드 세션 권한 상속 | **호환** |

### 왜 충돌하지 않는가?

**핵심 이유: 추상화 레이어가 다르다.**

```
┌─────────────────────────────────────────────┐
│ Layer 3: Agent Teams (OS 프로세스 레벨)       │
│   → 별도 claude 프로세스 간 협업              │
│   → 파일 시스템 기반 태스크/메일박스           │
├─────────────────────────────────────────────┤
│ Layer 2: Dynamic Chain (오케스트레이션 레벨)   │
│   → 체인 패턴에 따라 도구/에이전트 조합        │
│   → CLAUDE.md 지침 기반                      │
├─────────────────────────────────────────────┤
│ Layer 1: Subagents (도구 호출 레벨)           │
│   → Task() 도구로 서브에이전트 생성            │
│   → 단일 세션 내부에서 실행                    │
├─────────────────────────────────────────────┤
│ Layer 0: Claude Code Core (런타임)            │
│   → 도구 실행, 권한 관리, 컨텍스트 관리        │
└─────────────────────────────────────────────┘
```

- 커스텀 시스템 = **Layer 1~2** (세션 내부)
- Agent Teams = **Layer 3** (세션 외부)
- 서로 다른 레이어이므로 실행 로직이 겹치지 않음

## 3. 성능 비교

### 커스텀 시스템이 더 잘 수행하는 영역

| 강점 | 이유 |
|------|------|
| **모델 세분화 제어** | opus/sonnet을 에이전트별로 정밀 할당 |
| **체인 오케스트레이션** | 10개 체인 패턴으로 순차/병렬 최적 선택 |
| **낮은 토큰 비용** | 서브에이전트는 요약만 반환 (컨텍스트 절약) |
| **빠른 실행** | 프로세스 생성 오버헤드 없음 |
| **4-Layer 자동 분석** | Hook이 자동으로 최적 체인/에이전트 추천 |
| **메모리 시스템 통합** | 작업 결과 자동 저장/참조 |
| **즉시 사용 가능** | 별도 활성화 없이 CLAUDE.md만으로 작동 |

**최적 사용 시나리오:**
- 일상적 개발/분석 작업
- 단일 세션에서 완결되는 작업
- 순차적 의존성이 있는 워크플로우
- 비용 효율이 중요한 경우

### Agent Teams가 더 잘 수행하는 영역

| 강점 | 이유 |
|------|------|
| **진정한 병렬 실행** | 멀티 프로세스로 CPU 자원 활용 |
| **에이전트 간 직접 토론** | 가설 경쟁, 상호 반박 가능 |
| **독립 컨텍스트** | 각 팀메이트가 1M 토큰 컨텍스트 보유 |
| **장시간 독립 작업** | 메인 세션 컨텍스트 압박 없음 |
| **파일 소유권 분리** | 각자 다른 파일 담당으로 충돌 방지 |
| **사용자 직접 개입** | 개별 팀메이트에게 직접 지시 가능 |

**최적 사용 시나리오:**
- 대규모 코드 리뷰 (보안/성능/테스트 병렬)
- 경쟁 가설 디버깅 (여러 이론 동시 검증)
- 크로스 레이어 개발 (프론트/백/테스트 분리)
- 장시간 독립 리서치

## 4. 동시 사용 시나리오 (양립 가능)

Agent Teams를 활성화하더라도, 각 팀메이트가 CLAUDE.md를 로드하므로 커스텀 시스템이 그대로 작동한다.

```
┌─────────────────────────────────────────────────────┐
│  대규모 프로젝트 개발 (Agent Teams + 커스텀 체인)      │
├─────────────────────────────────────────────────────┤
│                                                     │
│  리드 세션 (Agent Teams)                             │
│  ├── 팀메이트 A: 프론트엔드                           │
│  │   └── 내부: WebDevChain+ 실행                     │
│  │       (system_architect → frontend-design          │
│  │        → webapp-testing → quality_reviewer)        │
│  │                                                   │
│  ├── 팀메이트 B: 백엔드                               │
│  │   └── 내부: DevChain 실행                          │
│  │       (requirements_analyst → system_architect     │
│  │        → code_developer → quality_reviewer)        │
│  │                                                   │
│  └── 팀메이트 C: 테스트/보안                           │
│      └── 내부: HotfixChain 실행                       │
│          (complexity_resolver → code_developer        │
│           → quality_reviewer)                         │
│                                                     │
│  팀메이트 간 직접 통신으로 조율                         │
│  각 팀메이트 내부에서 앤의 체인 시스템 독립 실행         │
└─────────────────────────────────────────────────────┘
```

## 5. 비유

| 비유 | 설명 |
|------|------|
| **앤의 시스템** | 한 명의 지휘자가 악기별 파트를 차례로/동시에 지시하는 **오케스트라** |
| **Agent Teams** | 여러 밴드가 각자 연습하고 서로 대화하며 합주하는 **멀티밴드 콜라보** |

둘 다 음악을 만들지만, 방식과 규모가 다르고 **함께 쓸 수도 있다.**
